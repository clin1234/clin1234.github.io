Paid in Cycles

What solving C++ and Rust challenges reveal about how a laptop will lie to you about performance wins.

01

Both languages

Blindly trusting wrong measurements

Your device and the validation server's may not be completely identical: plan for it

The obvious move, once you can build locally, is -march=znver2 (server uses Zen 2 CPU).

Not passing this flag will cause confusion due to disparate cycle counts from your device to the validation server. For example, when I designed a FIX-message parser, two of my solutions measured 16% apart on the laptop, and the "worse" one (storing the delimiter to a stack array and reloading it through different index registers) won locally because Alder Lake, my laptop CPU's microarchitecture, forwards store-to-load traffic cheaply. It lost on the validation server by 3%, because Zen 2's store forwarding is slower and its memory disambiguation weaker.

Lesson: local timing is a regression guard, not an optimization guide. It's valid for algorithmic changes, such as fewer instructions, fewer allocations, less memory touched. It's not valid for microarchitectural decisions: branchless vs. branch, store/reload vs. register residency, dependency-chain shape, unrolling. For those, read the generated assembly, and use llvm-mca.

Blindly porting a design from another language does not gurantee success

Whenever a challenge exists in both a C++ and a Rust version, don't assume the two harnesses agree on what a field even means. One pair here diverged because the C++ harness resets an internal counter before every operation so a venue always hands back the exact id its generator reserved, whereas a straight Rust port of the C++ version dropped that call while repurposing the same argument slot for something else, so an id that looks like "our own order" in the Rust version can name an unrelated one.

Calibrate you believe a single benchmark result

The wall-clock instruction (RDTSC here) doesn't necessarily tick at the core's actual frequency. On my laptop, the counter ran at a fixed 2.803 GHz while the core executed around 4.3–4.5 GHz, so every locally reported cycle count was quietly 1.56× too small.

You can measure such ratio directly: time a long chain of dependent multiplies (imul %r,%r chained, three cycles each in any modern core) with the harness's own clock read, and divide. Don't use a dependent add as the anchor: on at least one core (at least for me), it runs faster than the dependency should allow and gives a nonsense ratio.

Correcting this solved a long-running mystery: during a parsing challenge, a parser that was roughly 2× slower on the certified server turned out to be running at almost exactly the predicted speed: 415–447 local ticks × 1.558 landed within a rounding error of the actual certified score.

Widen the cycle model's dispatch width, or it will hide your best wins

If you reach for a static cycle-accuracy tool for the target microarchitecture, such as llvm-mca, check its default dispatch width against the target chip's. The Zen 2 model within the tool assumes 4-wide dispatch; the real Zen 2 CPU from the server retires up to six macro-ops/cycle. With the narrower default, the model saturates on dispatch and hides latency-chain improvements: a genuine 31% win (3.006 → 2.064 cycles per iteration, confirmed through disassembly) reported as a mere 6% one under the default width. Pass the wider dispatch explicitly whenever you're testing against the CPU; trust the narrow default only as a floor.

Don't treat certified submissions as merely rolling the same die multiple times

To quote the site's admin:

"The public benchmark you run locally and the private benchmark used for scoring on the server are completely different programs. They share the same challenge interface but measure different things under different conditions … it uses a different workload, different data, and different measurement methodology."HFT University forum, on a local/certified score mismatch

Any implementation whose cost depends on inputs staying inside the public generator's range is a landmine, such as a fast path gated to a parameter band, a series expansion that's only valid there, or a capacity overfitted to the public sample. For me, my implementation of an implied-volatility solver relied on a moneyness window and a bounded rate term; everything outside fell to a roughly 2,500-cycle bisection. On paper, the fast path was optimal. However, it simply never ran on certified data, and the score came back 16.6× worse than the local number.

Lesson: run your solution on a deliberately wide, off-distribution input and compare the throughput ratio against the shipped workload, not absolute time. If the ratio collapses once you're treding off the well-traveled path, you've defused the above landmine.

Read the scoring formula as a spec

Scoring tiers differ per challenge. Some challenges score a mean over a full run; some score the 99th percentile of latencies. At least one challenge doubles that percentile, because the harness's reported per-iteration operation count and the divisor against don't match, so a stated gold threshold of, say, 500 cycles actually requires a p99 of 250.

A percentile metric changes what's worth fixing, too. The average operation is irrelevant and so is the single worst one; what matters the most is which operation type contributes to the slowest 1%. That answer varies as you ierate: on one scheduler it shifted three times across a single project, from the "fire an event" path to a memory-access path to an "insert" path, so the overall approach isn't "measure once and optimize," it's "re-measure which type owns the tail after every change," because the next bottleneck is mostly like elsewhere in your solution.

Know the tick size

The certified runner's CPU clock ticks in coarse steps of about 31 cycles, so published scores can only be in multiples of 62. Save the sub-62 cycle micro-optimizations for changes you can already justify on other grounds, and don't consider "the score didn't move" as "the change didn't work" without checking whether it could have moved in the first place.

Never trust a single run on a machine that throttles

A one-shot comparison on a laptop that isn't thermally stable is closer to a coin flip than a measurement. Especially when switching between energy-saving and performance modes. My strongest example: a submission showed a +19.5% regression on a single run, which looked exactly like the "landmine tuned to the wrong workload" pattern, and would have been a plausible reason to revert a real improvement. Re-run properly paired, every candidate submission timed round-robin-style within the same challenge, and after tries: the same comparison came back −9.3% better. Two other apparent regressions in the same table vanished the same way. My experience: treat anything under a 2–3% difference as noise unless it survived a paired benchmark.

Don't waste the setup phase

Every allocation, every page fault, every table you can precompute belongs there instead of on the hot path. In my case, my string-map solution moved its table allocation into a untimed constructor and the cycle count dropped by roughly half.

Beware of two caveats, though. First, moving work the other way (say, hard-coding a struct size once its final size is known, which sounds like it should only help) can cost more than it saves if that lands inside the timed region instead of before it. Second, "untimed" does not mean "free of a clock entirely." An implementation that reconstructs an object and re-runs its setup on every one of a few hundred iterationsstill consumes wall-clock time limit on that submission, even though none of it touches the score.

A plausible solution is not a final result

A specific, reasoned prediction along the lines of "this should be faster because X" measured worse often enough that it's worth stating as a maxim: computing a value with pure mask arithmetic so a branch shouldn't exist at all cost 7% over just leaving the (nearly-always-not-taken) branch in place. Skipping a redundant memory write on a store-forwarding theory cost 15%. Splitting one fused loop into two cleaner passes cost more than the "wasted" work it was removing. They seemed to be acceptable steps, but every one of them shipped only after a paired measurement said no, and none of them would ne discovered by reasoning alone.

02

C++

What the compiler does at -O2, and what a Zen 2 CPU seeks.

Pack the key before you pick the container

Whenever a challenge caps key length at the width of CPU registers, a "string map" is secretly an integer map, and the solution becomes: load the bytes, and mask to the real length. No strcmp, no std::string, no byte loop within the hot path.

Masking to length prefers BZHI (one uop on Zen 2) rather than the more common PEXT/PDEP, which are slow there even though they look like the "correct" bit-manipulation instructions. BZHI has one caveat: its index saturates at the operand's own bit width. So asking a full 64-bit value with a 64-bit index silently clears the top bit: invisible on a 6-byte key (index never exceeds 48), but returns a wrong-answer when key length >= 8 bytes. A small lookup table of precomputed masks sidesteps the saturation case entirely and costs nothing on the hot path.

A per-op "don't optimize this away" barrier can hand back a value nobody wrote

An recurring pattern: call your operation, then pass the result through a compiler barrier that's meant to stop the whole call from being optimized away as dead code. For values that can't be stored in merely one register, GCC 14.2 with -O2 can satisfy that barrier by writing the result to one stack slot and then, read it back from a different stack slot that nothing wrote it to. It compiles cleanly, it passes a casual correctness check, and it fails always: moving the correctness check to before the barrier obscures it, which is why the bug can be shipped unnoticed.

One fix is to make the value exist in exactly one place the compiler has no freedom to re-derive: an inline-asm output register with memory clobbering, not a per-field atomic load (which can re-appear).

Not every branch wants to disappear

GCC will sometimes convert a branchless, masked value-select that you deliberatly wrote into a branch on the guarding condition (which, if unpredictable, reintroduces the cost you want to remove). To mitigate, force an unconditional load and select the result with an all-ones/all-zeros mask, which leaves the compiler nothing to branch on. Confirm it if worked by disassembling the generated hot loop.

A percentile metric can mask performance gains

An optimization that clearly improves the mean case ( such as eliminating a division from a per-item computation) can move a percentile-scored benchmark by nothing, if the workload's actual tail is dominated by a different operation entirely. Always check which operation type owns the top 1% after a change that "should" help, rather than assuming a mean-shaped win automatically shows up in a tail-shaped score.

For challenges involving only choosing build flags, learn which ones actually benefit

First, flag names lie about scope more than you'd expect, at least on GCC. -funroll-loops declines to unroll a loop whose trip count it can't determine statically, while -funroll-all-loops ignores that restriction.

Second, permission and mechanism are separate requirements, and you often need both. Breaking a single serial floating-point accumulation chain into independent partial sums needs GCC's permission to reassociate floating-point math at all (which needs two more flags to request) and a flag that actually hands each unrolled copy of the loop its own accumulator register:

-O2 -march=znver2 -fassociative-math -fno-signed-zeros -fno-trapping-math
                  # ^ the permission: reassociating FP math needs all three
    -funroll-all-loops -fvariable-expansion-in-unroller
                  # ^ the mechanism: actually unroll, then split the accumulator

Dropping a shared-library call boundary can remove more than a jump

GCC on Linux routes every call through a PLT stub with an indirect jump and (on a CET-enabled build) a landing-pad instruction that a Zen 2 core doesn't even need. Three flags reduced a five-taken-branch, four-endbr64 call sequence to three branches and zero stubs: -fno-plt removes the stub itself and, because the resulting GOT load target doesn't change across a tight loop's iterations, lets the compiler hoist that load out of the loop; -fvisibility=hidden on the callee makes the other boundary resolvable to a direct jump at link time, and -fcf-protection=none drops the landing-pad instructions the CPU has no use for. Also, verify with the linker's own relocation listing (a JUMP_SLOT count of zero is a useful sign) rather than trusting that the flags did what their names suggest.

On Windows with MinGW-w64 toolchain, every one of these flags does nothing, and the local benchmark numbers will look identical..

On a producer/consumer pipe, a faster producer can score worse

On challenges measuring end-to-end delivery latency through a queue (timestamp on push, read again on pop), Little's law dominates: latency equals how many messages are sitting in the queue, times how long each one takes the consumer to service. If the consumer is doing more work per message than the producer (reading a clock, updating a histogram, exactly what a benchmark harness does), a producer that gets faster only means the queue fills up quicker, which makes the score worse. Queues that reduces cycles out of the consumer's own path is not sufficient: without capping how deep the queue is, the score can land on the overflow sentinel.

A bounded wait inside the producer's own call is the approach, before it publishes: since the harness stamped the message before that call, the wait gets charged in full to the message that caused it. A misleading fix: a pause placed after the publish: it drains the queue just as effectively while being charged to no message at all.

Prefetch writes; be suspicious of prefetching reads

On a cross-core or cross-CCX ring, the producer's next write to a slot with a cold cache must acquire ownership of that cache line, and if that acquisition happens inside the measured window, the message pays for it. Issuing a write-intent prefetch several slots ahead of the current write moves that cost outside the window entirely, for free.

The consumer side is the opposite bet more often than it suggests. A read-ahead on the consumer takes a not-yet-consumed slot into a shared state early, which can force the producer's own publish to that slot into an invalidation. That reintroduces, from the other direction, the cost the producer-side prefetch was designed to remove. I got a gold submission on this kind of challenge by prefetching on the write side only, and adding a look-ahead read on the consumer measured worse in isolation.

On my laptop, where it can't reproduce true cross-core placement, a small sweep of the look-ahead depth is still worth running and evaluating:

One shared cache line beats two separate ones, when polling is also the delivery

The classic design for a cross-core marker-plus-payload handoff places the "is it ready" flag on its own cache line, separate from the data. That costs two serialized cross-core transfers per message: one to check the flag, another to fetch. Squishing the flag and the payload in the same 64-byte line collapses to one: the consumer's poll loop checks and fetches in the same cache line. Measured against a split-line version on an uncontended pair shows that it's roughly 3× worse on a straight read/write loop, and its p99 was 13x its own p50. The split design also occasionally stalls, which a percentile-scored challenge punishes with impunity.

Build the whole thing in registers before publishing

If a caller fills a struct field by field and then reads the whole struct back as one wide value to publish it, that incurs a store-to-load forwarding stall on the hot path: the store isn't guranteed to be committed by the time the wide load wants it. Assembling the value directly from values still within registers (using a vector-set intrinsic over the individual fields, rather than a load over the memory) eliminates that stall entirely. If the compiler tries to reorder that assembly wihtin the middle of a contincuous sequence of stores, an empty inline-asm barrier suffices.

Get runtime division out of anything that runs per element

Zen 2's integer division is not pipelined and costs around 40–60 cycles per operation. If the actual set of divisors a challenge can produce is small and bounded (a handful of named weight sets, say), resolvable with mere rightward bit shifts, and fall back to a precomputed reciprocal or the general case, you will see immense gains compared to a smattering of idivs on the hot path.

03

Rust

Rust, where no unsafe trickery is permitted.

Autovectorization is your only SIMD technique, and only one idiom reliably benefits from it

Because Rust challenges cannot include unsafe blocks, which discourages core::arch intrinsics, every vectorization opportunity comes solely from LLVM.

In my experience, only one idiom reliably benefits from this: state kept in fixed-size arrays over a block, with a simple for i in 0..BLOCK loop and the whole computation written out in the body. Two silent killers, with the consequence being roughly five times slower the ectorized version: any inner loop inside the block loop, even one with a small constant bound, and re-factoring the body into a helper function that takes a mutable reference as an out-parameter.

Box<[T; N]> plus a power-of-two mask elimates checking bounds

With get_unchecked being unavailable, the pattern that reliably removes a bounds check without unsafe is a heap array with a compile-time, power-of-two length (Box<[T; N]>, not Vec<T>, whose length can only be computed at run-time). The compiler can then prove the index is always in range and drops the check.

An index derived from internal bookkeeping (such as an allocated slot or a chain link) is safe to mask, because it's guranteed to be in range due to your choices and the mask merely confirms the gurantee. An index that arrives from outside your structure (such as an id, a symbol, anything caller-provided) can never be masked, because it silently aliases an out-of-range value onto a live slot instead of rejecting it. In this case, keep an explicit range check.

Make the conditional address, not the load

A data-dependent length or bounds check that's resembles a coin flip should be left out of the hot path, and the usual Rust idiom, if len >= N { wide read } else { narrow fallback }, yields that branch. Fix: make the pointer conditional instead of the control flow: try to obtain a reference to the wanted slice at the wanted offset, fall back to a reference to a static zero buffer otherwise, then read the reference. rustc and LLVM are free to lower the whole thing to conditional moves with the load itself folded into the selected one.

Two seemingly equivalent snippets can compile to different code

Some(v).filter(|_| cond) compiled branchless while both cond.then_some(v) and the explicit if cond { Some(v) } else { None } compiled to a real jump. The only reliable source of truth is the generated assembly.

"Not timed" doesn't mean "free of a clock"

In many challenges, benchmark harnesses construct a fresh instance of your solution and call its setup method inside the overall iteration loop, hundreds of times, even though only a small inner region of each iteration is what gets timed. But it still consumes harness's overall wall-clock timeout limit. In one challenge, a parameter search over several hundred candidates, run once per iteration, consumed more than half of its 60s time limit; it performed worse than setting a fixed constant.

When the bottleneck is integer ports, not memory, trading a load instruction wins

Assuming that a large table always implies "this is a memory problem" is wrong: check the actual port pressure before acting on it. On one string-map lookup, a cycle model showed four integer ALU ports fully saturated while the address-generation ports sat two-thirds of its runtime idle: the former contains a ALU-bound hot path disguised as a memory-bound problem. Once that was visible, the optimal solution deviated from intuition: replacing an integer multiply (three ALU instructions) with a small table lookup (one ALU instruction plus one memory access) was a net win specifically because it shifted work from saturated to idle ports, even though it technically added a memory access to a table.

Duplicate keys show performance degredation correctness issues

An append-only structure that never overwrites a repeated key looks correct (the first inserted value is still findable), until the key has hundreds of duplicates and future lookups for it has to walk the entire accumulated chain. Overwriting rather than appending fixed correctness and lookup regressions.

Fold the length in whenever fixed windows over a variable key overlap

Covering a variable-length key with a small number of fixed-width reads, such as reading the first eight bytes and the last eight bytes, is a branchless way to read a bounded key without a length-dependent loop. Also, two different short keys can produce byte-for-byte identical windows when looking at a few fixed positions. Folding the actual length into a data structure derived from those windows (a table-indexed salt works well, since its address depends only on a well-known value) restores the distinction for free, without adding anything to the dependency chain those byte loads are on.

Invalidate only the half of a cached result that could have changed

When a single update only affects one of two derived results (such as an update to one leg of a synthetic instrument feeding exactly one of an implied bid or an implied ask) cache both results separately and invalidate only the one the update actually touches. Recomputing both "to be safe" on every write throws away a two-to-four-times performance gain for no additional correctness, since the untouched half is still valid.
