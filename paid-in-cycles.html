Paid in Cycles

What solving C++ and Rust challenges reveal about how a laptop will lie to you about performance wins.

01

Both languages

Blindly trusting wrong measurements

Your device and the validation server's may be different

The obvious next step, once you can build locally, is -march=znver2 (server uses Zen 2 CPU).

If you won't pass this flag, expect the results to be confusing due to differences in cycle counts on your hardware and on the validation server. For example, when working on FIX-message parser implementation, two of my solutions differed by 16% locally, and the "worse" solution (using a stack array to store the delimiter and then reloading it through different index registers) won locally, because Alder Lake architecture (the one used in my laptop) forward stores-to-load operations efficiently, but lost by 3% on the server because Zen 2 is worse at this operation.

The takeaway from this experience is that the local timing is only useful for regression guarding. This method is valid for algorithmic improvements (e.g., less instructions, allocations, memory accesses), but not for microarchitectures-related improvements. For that, you'd have to read the generated assembly and use the llvm-mca.

Blindly porting a design from another language does not gurantee success

When both C++ and Rust versions of a challenge exist, never assume that both of them use the same definitions of fields used. In this particular challenge suite, one pair of implementations differed because the C++ harness reset an internal counter before each operation to make a venue return the exact id the generator assigned, while a naive port of the C++ version of the challenge lost this call to repurpose the corresponding argument.

Sometimes, calibrate on a single benchmark result

The wall-clock instruction (RDTSC in my case) does not necessarily tick in the core's frequency. In my case, the counter was ticking at 2.803 GHz, while the core frequency was 4.3-4.5 GHz. Thus, all my locally reported cycle counts were 1.56× smaller than in reality.

This ratio can be measured by time-based benchmarking: time a chain of dependent multiplies (imul %r, %r) chained (three cycles each in any modern core) using the harness's clock reading, and divide. Do not use dependent add instructions as a benchmark basis: on at least one CPU core, it will run faster than the dependency should allow.

By correcting this, I finally solved the old mystery: in one particular challenge where a parser performed 2× worse on certified server, I found out that it was almost exactly the expected speed: 415-447 cycles × 1.558 = the actual certified result (within rounding errors).

Widen the cycle model's dispatch width, or it will hide your best optimizations

In case you try a static cycle-accurate model for your target microarchitecture, such as llvm-mca, make sure that its default dispatch width is correct. The model of Zen 2 microarchitecture included in the tool assumes 4-wide dispatch, while the server uses 6-macro-ops-per-cycle CPU. The default dispatch width is too narrow and will saturate dispatch queue and hide any latency-chain improvements, such as a 31% improvement (from 3.006 to 2.064 cycles per loop, verified via disassembly), reported as a mere 6% improvement. Whenever you're benchmarking against a CPU, pass the wider dispatch explicitly; use the default width as a floor only.

Don't treat certified submissions as rolling the same die multiple times

To quote the site's admin:

"The public benchmark you run locally and the private benchmark used for scoring on the server are completely different programs. They share the same challenge interface but measure different things under different conditions … it uses a different workload, different data, and different measurement methodology."HFT University forum, on a local/certified score mismatch

Any implementation which depends on its inputs being within public generator's range is a trap, such as a fast path gated to a parameter band, a series expansion that is only valid there, or an overfitted capacity. In my case, the implementation of the implied-volatility solver I made relied on a moneyness window and bounded rate term; anything outside falls to a rough 2,500-cycle bisection algorithm. On paper, the fast path was optimal. However, it simply never fired on the certified data, and my certified score became 16.6× worse than the local one.

The lesson is simple: run your solution on a wide-range, off-distribution input and compare the ratio between the throughputs with the shipped workload, not the absolute time. If the ratio crashes, then your solution was triggered by the above trap.

Read the scoring formula as a spec

Scoring tiers differ per challenge. Scoring formula differs depending on the challenge. Some challenges use mean over the entire run as a score; others use the 99th percentile of latencies. At least one challenge double that percentile, as the reported per-operation count in the harness and divisor against it do not match, so if the gold score threshold is, say, 500 cycles, then the actual p99 is 250.

Also, a percentile metric makes optimization priorities different. Average operation is irrelevant, and so is the single worst one; what really matters is what operation type is the slowest 1%. This varies from iteration to iteration: in one scheduler implementation, it changed three times within one project, from the "fire an event" path to a memory-access path to the "insert" path, so the right way to deal with this challenge is not "measure once and optimize", but rather "re-measure which type owns the tail after each iteration", as the next bottleneck is most likely somewhere in your solution.

Know the tick size

Certified runner's CPU clock ticks in coarse steps of about 31 cycles, so published scores can only be in multiples of 62. Save the sub-62 cycle micro-optimizations for changes you can justify by other means, and do not assume that "the score didn't move" equals to "the change didn't work".

Never trust a single run on a machine that throttles

A one-run comparison on a computer that cannot be considered thermally stable is very close to flipping a coin. Especially, when you switch back and forth between power saving and performance modes. My best example: one of the submissions showed −19.5% regression on a single run, which looked like a textbook case of "tuned landmine to the wrong workload" and would have been a legitimate reason to undo a genuine improvement. Properly paired run for the same comparison resulted in +9.3%. Two other apparent regressions in the same table disappeared the same way. My rule: anything below 2-3% is likely noise, unless it survives paired benchmark.

Don't waste the setup phase

Every allocation, every page fault, and everything you can pre-compute goes into setup, rather than hot path. In my particular case, my string-map solution moved its table allocation into untimed constructor and cut the cycle count in half.

There are two caveats here. First, sometimes moving some work into untimed phase could hurt more than help. For instance, hard-coding the struct size when you know the final size sounds like something which should only improve it, until you realize it happens inside timed region, rather than outside. Second, "untimed" does not equal "free of any clock". If you allocate some objects and initialize them by re-running setup routine hundreds times, you still consume wall clock, despite none of it touching the score.

A plausible solution is not a final result

If you have a concrete and specific explanation on how the certain algorithm is supposed to be better ("this is better because...") and it turned out to be wrong, measured worse often enough that it's worth to state it explicitly: computing a value by pure mask operations to ensure that there is no branch at all costs 7% compared to leaving nearly-always-not-taken branch in place. Skipping redundant memory write based on a theory about store forwarding cost 15%. Splitting fused loop in two passes costed more than extra work it saved. They all looked like acceptable steps, but every single one of them was shipped only after proper paired measurement said "no" and could not have been discovered by reasoning alone.

02

C++

What the compiler does at -O2, and what a Zen 2 CPU seeks.

Pack the key before you pick the container

When masking to length, BZHI instruction (one micro-operation on Zen 2) is preferable to more common PEXT/PDEP instructions, which are quite slow there, despite looking like "correct" bit-manipulation operations. One caveat of BZHI: its index saturates at bit width of the operand itself. So requesting 64 bits length mask with 64 bit index would silently set the top bit to zero, which works fine for 6-byte keys (index never exceed 48), but returns a wrong answer for key lengths greater or equal 8 bytes. Lookup table with precomputed masks avoids the problem without any cost for hot path.

Per-operation "don't optimize this away" barrier can give you back a value nobody wrote

Recurring pattern: perform the operation and pass it to the compiler barrier which is supposed to prevent the entire call from being optimized as dead code. In case when the value is larger than can fit into just one register, GCC 14.2 with -O2 satisfies this barrier by writing the value into one stack slot and reading it from another stack slot which has never seen it. The code compiles cleanly, it passes casual correctness check and fails every single time: moving the check right before the barrier hides it, which allows shipping the bug without noticing.

One of the fixes is to make sure the value exists exactly in one place compiler cannot possibly derive: in inline assembly output register with memory clobbering, not atomic loads per field.

Not every branch wants to disappear

GCC will sometimes turn your explicit branchless selection by a masked value into a conditional branch with the same condition (which, if unpredictably, re-introduces the cost you wanted to eliminate). To prevent it, use an unconditional load followed by selection of the result with all-ones or all-zeros mask, thus giving nothing to branch on. Verify that it worked by inspecting the disassembly of the hot loop.

Percentile metric can mhide performance gains

Optimization that clearly improves the mean case (such as eliminating division from item computation) can make no visible difference in percentile-scored benchmark, if the workload's actual tail is dominated by completely different operation. Make sure you check which operation type dominates the top 1% after a change which "should" improve it, rather than assuming the mean-shaped gain automatically appears in percentile-shaped metric.

For challenges involving only choosing build flags, know which ones actually help

First, flag names lie about their scope more than you'd expect, at least for GCC. -funroll-loops refuses to unroll a loop when it cannot determine its static trip count while -funroll-all-loops ignores this restriction.

Second, permission and mechanism are different requirements and you might need both of them. Breaking a single serial floating point accumulation loop into independent partial sums requires GCC's permission to reorder the floating point operations at all (which, in turn, require two additional flags) and flag that actually gives each copy of the loop its own accumulator register: 

-O2 -march=znver2 -fassociative-math -fno-signed-zeros -fno-trapping-math
                  # ^ the permission: reassociating FP math needs all three
    -funroll-all-loops -fvariable-expansion-in-unroller
                  # ^ the mechanism: actually unroll, then split the accumulator

Dropping a shared-library call boundary can remove a branch

On GCC on Linux, every call goes through a PLT stub with an indirect jump, and (on a CET-enabled build) a landing-pad instruction, which is useless for a Zen 2 CPU. Three flags trimmed a five branch sequence to three branches and zero stubs: -fno-plt removes the stub itself,and hoists the GOT load, whose target does not change across tight loop iterations; -fvisibility=hidden on the callee resolves the other boundary to a direct jump at link time; and -fcf-protection=none drops the landing-pad instructions the CPU doesn't care about. And make sure, using the linker's relocation list (a zero JUMP_SLOT count is a good indicator), that it actually happened.

None of these flags works on Windows under the MinGW-w64 toolchain, and the local numbers will be exactly the same.

In a producer/consumer pipe, a faster producer can perform worse

On challenges measuring end-to-end delivery latency through a queue (timestamp the message push, read the timestamp again on pop), Little's law holds: latency is the number of messages in the queue times the service time per message. If the consumer is handling more work per message than the producer (such as stamping the message's timestamp and updating a histogram, exactly the job the benchmark harness does), the faster producer just results in more queued messages and a worse score. Queues that optimize the consumer's workload alone are not sufficient: without bounding the size of the queue, the overflow sentinel is the only possible score.

The solution is to add a bounded wait in the producer's call, before it publishes: since the harness stamps the message before the call, the wait will be fully charged to the message that caused it. Misleading solution: a delay in the producer after the publish: it will drain the queue in the same way, but with no message charged for it at all.

Prefetch writes; be suspicious of prefetching reads

For a cross-core or cross-CCX communication, the producer's write to a slot with a cold cache line must acquire the ownership of the line. If that occurs in the measurement window, the message will pay for that. Prefetching the next slot's line in advance will move that cost entirely outside the window, for free.

On the consumer side, it is the opposite. A read-ahead of the consumer takes the yet-unconsumed slot into a shared state early, which forces the producer's write to that slot to become an invalidation. This reintroduces, from the other side, the cost the producer-side prefetching was supposed to get rid of. I won a gold submission in this challenge by prefetching only in the producer side, and adding a look-ahead read in the consumer measured worse in isolation.

One cache line is better than two, when polling is the delivery mechanism too

A traditional approach for designing a cross-core marker-payload handoff places the "ready" flag on a different cache line than the payload. It involves two serialized cross-core communication operations: one for the check and the other for the fetch. Placing the flag and the payload in the same 64-byte cache line reduces the cost to one: the consumer's poll loop checks and fetches from the same cache line. Compared with a split line version on an uncontested pair, this design proved to be about 3× worse on a straight read/write cycle, and its p99 latency was 13× its p50 latency. Split design also stalled, which hurted the performance on the percentile-based challenge.

Build the whole struct in registers before publishing it

If a function fills the structure field by field and then reads it back as a wide value to publish it, it incurs a store-to-load forwarding stall on the hot path: the store is not guaranteed to commit until the wide load reads it. Building the value directly from the values still in the registers (using a vector_set intrinsic on the individual fields instead of reading the structure memory) removes that stall. If the compiler attempts to reorder that construction in the middle of a continuous sequence of stores, an empty inline asm barrier will suffice.

Remove runtime divisions from any code that runs per element

The integer division in Zen 2 architecture is not pipelined and costs about 40–60 cycles per operation. If the set of divisors the challenge generates is small, bounded (a few named weight sets, for example), and resolvable with simple right shifts and fall back to either a precomputed reciprocal or general case, the gains would be enormous compared to the idiv instructions sprinkled here and there.

03

Rust

Rust, where no unsafe trickery is permitted.

Autovectorization is your only SIMD technique, and only one idiom reliably benefits from it

Because Rust challenges cannot include unsafe blocks, which discourages core::arch intrinsics, it leaves vectorization opportunities to LLVM alone.

In my experience, only one idiom reliably uses this: a state held in a fixed-size array over a block, with a simple for i in 0..BLOCK loop and computation written completely inside its body. Silent killers: about five times slower vectorized variant: any inner loop inside block loop (even with a small constant bound), and refactoring the body to a helper function taking a mutable reference to it.

Box<[T; N]> plus power-of-two mask elimates bounds checks

With get_unchecked being off-limits, the reliable way to remove a bounds check without unsafe is a heap array with a compile-time, power-of-two length (Box<[T; N]>, not Vec<T>, whose length is only computable at run-time). The compiler can then prove the index is always within bounds and drops the check.

The index calculated from internal bookkeeping (such as allocated slot, or a chain link) is safe to mask, as it guaranteed to be within bounds due to your choices and the mask only confirms the guarantee. An index that comes from outside your structure (such as an id, or a symbol, or whatever else provided by a caller) can never be masked, as it silently creates an alias to an out-of-bounds value instead of rejecting it. In this case, keep the explicit bounds check.

Make the conditional address, not the load

Data-dependent length or bounds check that looks like a coin toss should be off the hot path, and the usual Rust idiom, if len >= N { wide read } else { narrow fallback }, does exactly that. Fix: instead of making the control flow conditional, make the pointer conditional, trying to obtain the reference to the wanted slice at the wanted offset, falling back to the reference to a static zero buffer if failed, then reading the reference. rustc and LLVM are then free to compile it to conditional moves where the load itself becomes a part of the selected one.

Two seemingly equivalent snippets can compile to different code

Some(v).filter(|_| cond) compiled branchless, while both cond.then_some(v) and the explicit if cond { Some(v) } else { None } compiled to an actual jump. The only reliable source of truth is the generated assembly.

"Not timed" doesn't mean "free of a clock"

Many challenges have benchmark harness that builds a new instance of your solution and calls its setup method inside the main iteration loop, hundreds of times, even though only a small region of each iteration is actually timed. But it still takes time from the overall wall-clock timeout limit. In one particular challenge, an exhaustive parameter search over several hundred candidates, run once per iteration, used more than half of its 60s timeout limit and performed worse than setting a fixed constant.

If the bottleneck is integer ports, not memory, trading a load instruction wins

Assuming that a big table always means "this is a memory problem" is incorrect: analyze the actual port pressure before acting on it. On one string map lookup, the cycle model revealed four integer ALU ports being fully saturated, while the address generation ports were only 2/3 busy throughout the whole run: there was a ALU-bound hot path disguised as a memory-bound problem. Once that became clear, the optimal solution went against common sense: substituting an integer multiply (three ALU instructions) with a small table lookup (one ALU instruction and one memory access) turned out to be a net win specifically because it shifted work from saturated to idle ports, even though it introduced one additional memory access to the table.

Duplicate keys show performance degredation and correctness issues

An append-only structure that never overwrites a duplicate key looks good (the first inserted value will be still found), until the key has hundreds of duplicates and future lookups for it has to go through the entire accumulated chain. Overwriting instead of appending solved both correctness and performance problems.

Fold the length in whenever fixed windows over a variable key overlap

Reading a bounded key through a small number of fixed-width reads, such as the first and last 8 bytes, is a branchless way to read the bounded key without length-dependent loop. Also, two different short keys can generate byte-by-byte identical windows when viewed at some fixed positions. Folding the actual length into a data structure calculated from those windows (table indexed salt works well here, as its address depends only on a well-known value) gives you a free restoration of the uniqueness, without introducing anything into the dependency chain of those byte loads.

Invalidate only the half of a cached result that could have changed

If an update affects only one of two calculated results (for example, an update to one leg of a synthetic instrument affects only one of an implied bid or an implied ask), cache both results separately and invalidate only the one affected. Recalculating both "to be sure" after every write discards a two-to-four times speed-up for nothing, as the other half stays valid anyway.
